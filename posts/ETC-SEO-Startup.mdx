## 1. 왜 SEO를 다시 들여다보게 됐을까

초기 스타트업이다 보니 마케팅 예산이 넉넉하지 않았다. 유료 마케팅에 계속 의존할 수 있는 구조도 아니었다. 그래서 검색을 통한 자연 유입을 어떻게든 늘려야 한다는 생각이 강하게 들었고, 그때 관련 코드를 다시 열어보면서 현재 문제점과 개선 할 수 있는 것들을 정리하기 시작했다.

입사 초기에는 외주로 개발된 코드베이스를 이어받은 상태였는데, 메타 태그가 전역에 하나만 설정되어 있었다.
페이지마다 다른 콘텐츠를 담고 있는데도 검색엔진에게는 전부 같은 페이지처럼 보이고 있었던 셈이다.
그래서 각 페이지별로 메타태그를 달아주는 정도의 처리만 해놓은 상태였다.

많이 고민하고 또 많이 공부했다. 왜 우리 서비스는 검색엔진 순위에서 항상 밀려 있을까?
서비스의 신뢰도인가? 아니면 내가 제대로 검색엔진 최적화를 하지 못 했나? 하는 생각이 들었던 것 같다.
SEO라는 단어는 익숙한데 실제로 무엇을 어떤 순서로 해야 효과가 있는지는 따로 정리해본 적이 없었다.

그러던 중 FECONF에서 진행한 [1년에 10억 원을 절약한, 강남언니의 SEO 웹 전략 공개](유튜브%20링크) 영상을 보게 됐고, 이 영상을 계기로 SEO를 하나씩 체계적으로 다시 공부하기 시작했다. 이 글은 그 과정에서 실제로 적용해본 것들, 그리고 아직 적용하지 못하고 남겨둔 것들을 정리한 기록이다.

## 2. 액션마다 반영되는 속도가 다르다

처음에는 뭔가를 고치면 며칠 안에 검색 결과에도 바로 반영될 거라고 막연히 생각했다. 그런데 실제로는 그렇지 않았다.

메타 태그를 고치거나 캐노니컬을 설정하는 것처럼 크롤링/인덱싱 신호에 직접 관련된 액션은 짧으면 2~3일 안에 서치 콘솔에서 변화가 보이기도 했다. 반면 코어 웹 바이탈 개선이나 백링크처럼 사이트의 신뢰도, 흔히 말하는 "권위"와 관련된 영역은 훨씬 더 오래 걸렸다.
구글이 사이트를 재평가하는 데 시간이 걸리기 때문인 것 같은데, 체감상으로도 몇 주에서 몇 개월까지 걸리는 걸 지켜봐야 했다.

이 차이를 모르면 "이만큼 했는데 왜 아무것도 안 바뀌지"라는 조급함에 빠지기 쉽다. 그래서 작업을 시작하기 전에 이게 단기적으로 반응이 올 영역인지, 장기적으로 지켜봐야 할 영역인지부터 구분해보는 게 먼저라고 생각한다.

## 3. 크롤링과 인덱싱의 정확한 이해

크롤링은 구글봇이 페이지를 방문해서 콘텐츠를 수집하는 것이고, 인덱싱은 그렇게 수집한 콘텐츠가 검색 결과에 노출될 수 있는 상태로 등록되는 것이다. 이 둘은 같은 게 아니어서, 크롤링이 잘 되고 있다고 해서 검색에 노출되는 것도 아니다.

서치 콘솔의 페이지 리포트를 보다 보면, 크롤링은 됐는데 인덱싱에서는 제외된 페이지들이 꽤 있다는 걸 알게 된다. 처음에는 왜 이런 페이지가 있는지 이해가 안 됐는데, 구글이 페이지를 검색 결과에 올리기까지 거치는 단계를 나눠보면 좀 더 명확해진다.

- **발견되지 않음** — 구글이 아직 이 URL의 존재 자체를 모르는 상태
- **발견됨** — 사이트맵이나 링크를 통해 URL을 인지했지만 아직 방문 전인 상태
- **크롤링됨** — 구글봇이 실제로 페이지를 방문해 콘텐츠를 수집한 상태
- **인덱스됨** — 수집한 콘텐츠가 검색 결과에 노출될 수 있는 상태로 등록된 상태

크롤링됨과 인덱스됨 사이에는 분명한 간극이 있다.

그래서 SEO 개선의 첫 단추는 "얼마나 빨리, 얼마나 많이 중요한 페이지가 크롤링되게 만드느냐"라고 봤고, 이게 크롤링 버짓이라는 개념으로 이어졌다.

## 4. 크롤링 버짓 아껴쓰기

크롤링된 페이지가 많아질수록 인덱싱될 기회도 늘어난다.

그래서 SEO 개선의 첫 단추는 "얼마나 빨리, 얼마나 많이 중요한 페이지가 크롤링되게 만드느냐"였고, 여기서 나오는 개념이 **크롤링 버짓**이다.

**크롤링 버짓**은 구글봇이 한 사이트를 방문했을 때 쓸 수 있는 시간과 리소스의 한도다.
사이트가 크거나 서버 응답이 느리면 구글봇이 한 번에 수집할 수 있는 페이지 수가 줄어든다. 결국 한정된 리소스를 어떻게 하면 정말 중요한 페이지에 우선적으로 쓰이게 만들 것인가의 문제였다.

그래서 다음 네 가지를 진행했다.

1 . _이미지 최적화_

서버 응답이 느려지는 건 크롤링 버짓 입장에서도 손해였다. 그래서 LCP와 FCP를 개선하는 쪽으로 접근했는데, 그중에서도 이미지 쪽 작업의 비중이 컸다.

일단 png, jpg 같은 이미지 파일들을 WebP로 변환했다. WebP는 같은 화질에서 파일 크기가 JPEG나 PNG보다 25~35%가량 작다고 알려져 있는데, 이미지가 많이 들어가는 아이템 목록·상세 페이지에서는 이 차이가 누적돼서 체감이 꽤 컸다.

**next/image**의 lazy loading도 같이 썼다. 뷰포트 밖에 있는 이미지는 스크롤로 가까워지기 전까지 요청을 미루기 때문에, 첫 화면을 그리는 데 필요한 리소스와 경쟁하지 않는다. 특히 이미지가 여러 장 나열되는 목록 페이지에서 초기 로딩 부담을 줄이는 데 효과적이었다.

이 두 가지를 합치면 거창한 작업은 아니었지만, 초기 렌더링에 걸리는 시간을 줄이는 데는 확실히 도움이 됐다.

2 . _크롤링 대상에서 의도적으로 제외하기_

검색 결과에 노출될 필요가 없는 페이지들도 있었다. 로그인 이후에만 접근 가능한 마이페이지, 회원가입 페이지, 로그인 페이지 같은 것들이다. 이런 페이지들은 각 페이지의 메타데이터에서 **noindex**를 지정해 크롤링 대상에서 빼뒀다.

```tsx
// app/mypage/page.tsx
export const metadata = {
  robots: {
    index: false,
    follow: false,
  },
};
```

이렇게 확보한 크롤링 리소스는 그만큼 진짜 중요한 페이지 쪽으로 쓰인다.

3 . _캐노니컬로 대표 페이지 정리하기_

정렬 옵션이나 페이지네이션, UTM 파라미터가 붙으면서 같은 콘텐츠를 가리키는 URL이 여러 개 생기는 경우가 있었다. 캐노니컬은 이렇게 내용은 같은데 주소만 다른 페이지들 중에서 "이게 대표 URL이다"라고 검색엔진에 알려주는 태그다. 이걸 명시해두면 구글이 같은 콘텐츠를 여러 개의 별도 페이지로 인식해서 리소스를 낭비하는 걸 막는 역할을 했다.

4 . _사이트맵 분할_

사이트맵은 사이트 안에 어떤 페이지들이 있는지 구글에게 목록으로 알려주는 파일이다. 기존에는 이 사이트맵이 하나로 뭉쳐 있어서 우선순위를 파악하기 어려웠다. 그래서 페이지 경로의 상위 도메인을 기준으로 사이트맵을 나눴다. 예를 들면 _/product/1_, _/product/2_ 처럼 _product_ 하위에 있는 페이지들은 전부 **product** 사이트맵 하나로 묶고, 이렇게 나눈 개별 사이트맵들을 상위 사이트맵 인덱스에서 관리하는 식이다.

## 5. JSON-LD와 검색 결과 클릭률

크롤링과 인덱싱까지 해결됐다고 해서 끝이 아니었다. 검색 결과에 노출이 돼도 사람들이 클릭하지 않으면 의미가 없다. 이 지점에서 JSON-LD로 구조화된 데이터를 넣는 작업을 했다.

JSON-LD는 이 페이지가 어떤 종류의 콘텐츠인지를 검색엔진에게 명시적으로 알려주는 방식이다. 이게 잘 반영되면 검색 결과에 별점, FAQ, 브레드크럼 같은 리치 스니펫이 노출되면서 일반 텍스트 결과보다 눈에 더 잘 띈다.

```tsx
function ItemFaqJsonLd({
  faqs,
}: {
  faqs: { question: string; answer: string }[];
}) {
  const jsonLd = {
    '@context': 'https://schema.org',
    '@type': 'FAQPage',
    mainEntity: faqs.map((faq) => ({
      '@type': 'Question',
      name: faq.question,
      acceptedAnswer: {
        '@type': 'Answer',
        text: faq.answer,
      },
    })),
  };

  return (
    <script
      type="application/ld+json"
      dangerouslySetInnerHTML={{ __html: JSON.stringify(jsonLd) }}
    />
  );
}
```

실제로 적용한 스키마는 페이지 성격에 따라 조금씩 달랐다. 메인 페이지에는 _Organization_, 리뷰 페이지에는 _Review_, 아이템 소개 페이지와 입주 지식인 페이지에는 _FAQPage_, 메인 페이지의 아이템 가이드 캐러셀 컴포넌트에는 *ItemList*를 적용했다.

JSON-LD가 노출되는 페이지들을 기준으로 봤을 때 CTR이 체감상 1.3~1.5배 정도 올랐다고 느꼈는데, 정확한 수치라기보다는 서치 콘솔 성과 리포트를 보면서 느낀 정도라고 봐주면 좋을 것 같다.

## 6. 시맨틱 태그와 콘텐츠 구조

시맨틱 태그는 원래도 어느 정도 신경 쓰면서 작성해왔다. _div_ 로만 채우기보다는 _header_, _nav_, _main_ 같은 태그를 써왔다. 그런데 막상 "이걸 제대로 안 지키면 정확히 어떤 불이익이 있는가"라고 물으면 자신 있게 답하지 못했다. 그래서 이번 기회에 좀 더 파고들어 봤다.

**시맨틱 태그**(_header_, _nav_, _main_, _article_, _section_ 등)는 검색엔진이 크롤링해간 HTML에서 어디가 메뉴나 배너 같은 보일러플레이트이고 어디가 실제 본문인지 구분하는 단서로 쓰인다. *div*로만 채워진 페이지는 이 구분이 애매해서, 본문과 무관한 텍스트까지 콘텐츠 관련성 판단에 섞여 들어갈 수 있다. 구조가 명확하면 검색엔진이 특정 섹션을 그대로 인용하기도 쉬워지는데, 검색 결과의 스니펫이나 "특정 구간으로 바로가기"처럼 구조화된 콘텐츠를 활용하는 기능들이 여기서 갈린다.

최근에는 생성형 AI가 답변을 만들 때도 비슷한 구조를 활용하는 것 같다. 본문 경계가 명확한 페이지일수록 어떤 문단을 요약하고 인용해야 할지 AI 입장에서도 판단하기 쉬워지기 때문에, GEO(생성형 엔진 최적화) 관점에서도 챙겨둘 만한 부분이다. 다만 이것도 순위를 직접 끌어올리는 요인이라기보다는, 검색엔진이나 생성형 AI가 콘텐츠를 의도한 형태로 정확히 활용할 확률을 높이는 쪽에 가깝다.

검색엔진이나 AI 쪽 이유만 있는 것도 아니다. 태그를 일관되게 쓰면 코드를 읽는 사람 입장에서도 구조가 한눈에 들어온다. *div*로만 쌓여 있으면 이 부분이 헤더인지 본문인지 마크업만 봐서는 알기 어려운데, _header_ / _main_ / _article_ 처럼 의미가 담긴 태그를 일관되게 쓰면 마크업 자체가 문서처럼 읽힌다. 여러 명이 같은 코드베이스를 만지는 상황에서는 이런 일관성이 서로의 코드를 파악하는 속도에도 영향을 준다.

정리하면 시맨틱 태그를 지켜야 하는 이유는 크게 두 가지다. 검색엔진이나 생성형 AI가 콘텐츠를 정확히 활용하게 만드는 것, 그리고 함께 코드를 보는 사람들이 구조를 더 빠르게 파악하게 만드는 것이다.

## 7. 장기적으로 쌓이는 사이트 권위

여기서부터는 결과를 바로 확인하기 어려운, 시간이 걸리는 영역이다.

**코어 웹 바이탈**

LCP, FID, CLS 세 지표는 서치 콘솔에서도 [별도 리포트](https://developers.google.com/search/docs/appearance/core-web-vitals?hl=ko)로 다룰 만큼 비중 있게 취급되는 것 같다.

실제로는 세 가지 작업을 진행했다.

번들 사이즈가 크면 브라우저가 JS를 내려받고 파싱하고 실행하는 데 시간이 걸리고, 그만큼 화면에 의미 있는 콘텐츠가 그려지는 시점인 LCP도 늦어진다. 그래서 코드 스플리팅으로 초기 번들에 꼭 필요한 코드만 남겼다. 초기 렌더링에 필요 없는 컴포넌트, 예를 들면 클릭해야만 열리는 모달 같은 건 굳이 첫 번째 번들에 포함시킬 이유가 없었다.

```tsx
import dynamic from 'next/dynamic';

const ReviewWriteModal = dynamic(() => import('./ReviewWriteModal'), {
  ssr: false,
});
```

이렇게 분리해두면 모달을 열기 전까지는 해당 코드가 아예 로드되지 않으니, 초기 번들 크기와 LCP 둘 다에 도움이 됐다.

초기 렌더링에 당장 필요하지 않은 스크립트는 **defer**로 처리했다. 스크립트가 HTML 파싱을 막고 있으면 그만큼 첫 콘텐츠가 그려지는 시점이 밀리기 때문에, 화면을 그리는 데 당장 필요하지 않은 스크립트는 파싱이 끝난 뒤 실행되도록 미뤘다.

API 응답을 기다리는 비동기 UI에는 스켈레톤 UI를 넣었다. 응답이 오기 전까지 비어 있다가 응답이 온 뒤 갑자기 콘텐츠가 들어차면 레이아웃이 밀리는데, 이게 CLS다. 스켈레톤으로 미리 공간을 잡아두면 이 밀림을 막을 수 있다.

폰트 로딩도 코어 웹 바이탈에 영향을 주는 부분이라 함께 손을 봤다. 폰트 포맷을 WOFF2로 통일하고, 실제로 쓰는 weight만 남겨서 불필요한 파일을 줄였다. 폰트가 늦게 로드되는 동안 텍스트가 안 보이는 현상을 막기 위해 **font-display: swap**을 적용했고, 첫 화면에서 바로 보이는 핵심 폰트는 preload까지 고려했다. Next.js 환경이라 이런 처리 대부분을 **next/font**로 해결할 수 있었다.

```tsx
import { Noto_Sans_KR } from 'next/font/google';

const notoSansKR = Noto_Sans_KR({
  subsets: ['latin'],
  weight: ['400', '700'],
  display: 'swap',
});
```

**next/font**를 쓰면 폰트 파일을 빌드 타임에 최적화해서 제공하고, 레이아웃에 적용한 폰트는 자동으로 preload까지 처리해줘서 직접 신경 써야 할 부분이 많이 줄었다.

**외부 링크**

신뢰도 높은 외부 매체에서 링크를 받는 건 도메인 권위에 기여한다. 실제로 우리 서비스의 백링크는 주로 언론 보도를 통해 확보됐는데, 이건 운영팀에서 주도한 작업이라 내가 직접 관여하지는 않았다.

**페이지 사일로 구조**

특정 주제에 대한 허브 페이지와 세부 콘텐츠 페이지들을 내부 링크로 촘촘하게 엮어서, 검색엔진이 그 주제에 대한 사이트의 전문성을 인식하게 만드는 구조를 페이지 사일로라고 한다. 의도적으로 설계한 적은 없었는데, 개념을 알고 나서 우리 페이지들을 다시 살펴보니 관련된 페이지들끼리 내부 링크로 연결된 경우가 이미 일부 있었다. 다만 사일로 구조를 노리고 만든 게 아니라 콘텐츠를 채우다 보니 자연스럽게 생긴 결과에 가까워서, 허브 페이지를 중심에 두고 의도적으로 설계하는 것과는 다르다.
우리 서비스에 대입해보면 "입주 준비 가이드" 같은 허브 페이지 아래 "이사 체크리스트", "인테리어 시공 순서", "입주 청소 팁" 같은 세부 페이지들을 의도를 갖고 연결하는 구조를 그려볼 수 있을 것 같다.

이 세 가지 영역을 모두 지켜보면서, 키워드 기준으로 순위가 움직이는 걸 체감을 얘기하자면 짧게는 2주, 길게는 2개월 정도 걸렸던 것 같다. 다만 이건 순위 변동을 기준으로 한 체감이고, 도메인 권위 자체가 쌓이는 데는 이보다 더 오래 걸릴 거라고 생각한다.

## 8. 지역×시공 아이템 조합 페이지로 늘린 유입

헬로입주는 입주 시공 서비스다 보니 지역마다 광고 키워드도 다르게 운영했고, 시공 비용 자체도 지역별로 차이가 컸다. 수도권과 비수도권 정도의 큰 구분이 아니라, 같은 수도권 안에서도 시·군·구마다 단가가 달랐다.

그래서 지역과 시공 아이템을 조합한 페이지를 만들어서 사이트맵에 추가했다. 시 + 아이템, 시군 + 아이템, 시군구 + 아이템, 이렇게 세 단계로 조합해서 행정구역 단위별로 페이지가 생기게 했다. 예를 들면 "서울시 입주청소 비용", "수원시 입주청소 비용", "수원시 팔달구 입주청소 비용"처럼 지역 단위가 세분화될수록 더 구체적인 페이지가 만들어지는 식이다. 이 조합만으로도 페이지 수가 꽤 많이 늘었다.

각 페이지 하단에는 FAQ 섹션을 두고, 해당 지역의 평균 시공 단가를 적어뒀다. 이 FAQ를 4번에서 다룬 사이트맵 분할, 5번에서 다룬 **FAQPage** 스키마와 같은 방식으로 JSON-LD 마크업해서, 검색 결과에도 지역별 평균 단가가 바로 노출되게 만들었다. 예를 들면 이런 식이다.

- Q: 수원시 팔달구 입주청소 시공 평균 비용은 얼마인가요?
- A: 수원시 팔달구 기준 입주청소 시공 평균 비용은 OOO만원입니다.

지역명과 가격이 질문·답변에 그대로 들어가다 보니, 검색 결과 단계에서부터 "얼마인지"가 바로 보였다.

검색하는 사람이 가장 궁금해하는 건 결국 가격이다. 그 답을 검색 결과에서 먼저 보여준 페이지들은, 일반 JSON-LD 적용 페이지들보다 CTR이 눈에 띄게 높았다. 검색 결과 단계에서 이미 원하는 정보를 확인하고 들어오니, 클릭으로 이어지는 비율 자체가 달랐던 것 같다.

## 정리하며

SEO 작업에서 중요한 건 이걸 하나로 뭉뚱그리지 않고, 지금 하는 게 크롤링/인덱싱 문제인지, 클릭률 문제인지, 아니면 장기적인 권위 문제인지부터 구분하는 것이다. 이 구분이 없으면 뭘 해도 효과가 없는 것처럼 느껴지기 쉬운데, 실제로는 그냥 반응이 늦게 오는 영역일 뿐인 경우가 많다.

아웃바운드 링크 품질 관리나 페이지 사일로처럼 의도를 갖고 설계하지 못한 영역들은, 개발자 혼자 판단해서 진행하기보다는 콘텐츠나 마케팅 쪽과 함께 방향을 잡아야 하는 영역이라는 생각이 든다. 이런 작업을 프론트엔드 개발자가 어디까지 주도적으로 제안하고, 어디서부터는 다른 팀의 영역으로 넘겨야 하는지는 아직 정리가 안 된 질문으로 남아있다.
